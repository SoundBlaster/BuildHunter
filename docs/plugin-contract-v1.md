# Контракт плагина v1

Статус: **предложение `1-draft.1` для review**, 2026-10-13. Это конкретизация
[модульной архитектуры](modular-architecture.md), а не реализованный plugin runtime.
JSON Schema и примеры проверяются отдельно; Rust evaluator, Swift SDK и загрузчик
в приложении ещё предстоит написать. Предлагаемые изменения поведения отмечены
в разделе миграции и не меняют текущую сборку BuildHunter.

## 1. Что должен уметь автор

Автор описывает признаки нужного объекта, даёт ему стабильный ID и прикладывает
проверочные примеры. Он может добавить новые имена папок и маркеров без правки
scanner. Например: «папка `target` рядом с обычным файлом `Cargo.toml` — результат
сборки Rust».

Автор не управляет обходом, потоками, чтением содержимого, измерением, удалением
или UI. Если признака нельзя выразить поддерживаемыми фактами, требуется расширить
контракт движка. Неизвестная возможность диагностируется при загрузке пакета.

## 2. Два уровня данных

**Rifle program** — абстрактная программа проверки: типизированные входные факты
и именованные правила. Rifle не знает, откуда пришёл факт `project`, что означает
`rust.target` и где находится файл. Программа возвращает результаты правил.

**BuildHunter plugin** — оболочка вокруг программы. Она связывает факты с
операциями получения данных и результаты правил — с типами находок приложения.
Оболочку загружает BuildHunter; Rifle получает только поле `program`.
Так filesystem vocabulary не становится зависимостью Rifle.

Формат пакета для первой версии — один UTF-8 JSON-документ. Его schema:
[plugin.schema.json](contracts/plugin-v1/plugin.schema.json); вложенная программа:
[rifle-program.schema.json](contracts/plugin-v1/rifle-program.schema.json).
Fixtures хранятся рядом в репозитории автора, но не загружаются сканером.
Архивы, вложенные ресурсы, scripts и ссылки на другие пакеты в v1 отсутствуют.

| Поле пакета | Контракт |
|---|---|
| `format` | Точная версия `buildhunter.plugin/1-draft.1`; никакого угадывания версии |
| `id` | ID пакета, например `org.buildhunter.rust`; глобально уникален в каталоге |
| `version` | Тройка целых `major.minor.patch`, без ведущих нулей; в этом draft без prerelease/build suffix |
| `title`, `description` | Обычный текст для человека; не команды и не HTML |
| `program` | Программа `rifle.program/1-draft.1` |
| `bindings` | Для каждого факта ровно один источник данных, поддерживаемый BuildHunter |
| `targets` | Типы находок: ID, заголовок, ecosystem, kind и ссылки `ruleIds` |

ID состоят из ASCII lowercase букв, цифр, точек и дефисов, начинаются с буквы,
максимум 128 символов. ID пакета и типа находки стабильны между обновлениями;
локальные ID правил уникальны внутри программы. Один rule ID может принадлежать
ровно одному target. Target может объединять несколько правил через логическое OR.
Неиспользованные правила и факты запрещены, чтобы план не собирал лишние данные.

`ecosystem` — расширяемый ID группы, например `rust` или `example.forge`.
Неизвестная группа получает обычную подпись и стандартную иконку; добавление
экосистемы не требует изменения enum языков в движке. `kind` в v1 ограничен
`build_output`, `cache`, `environment`, `bytecode`, `metadata`; отображение
принадлежит приложению. Плагин не добавляет произвольный UI или поведение действия.

## 3. Полный пример

[Пример Rust](contracts/plugin-v1/examples/rust.json) содержит программу с тремя
фактами: `name: string`, `kind: string`, `project: boolean`. Её условие:

```json
{
  "all": [
    { "fact": "kind", "op": "eq", "value": "directory" },
    { "fact": "name", "op": "eq", "value": "target" },
    { "fact": "project", "op": "eq", "value": true }
  ]
}
```

Связи фактов с источниками:

```json
{
  "name": { "source": "node.name" },
  "kind": { "source": "node.kind" },
  "project": { "source": "marker", "scope": "parent", "name": "Cargo.toml" }
}
```

Совпадение локального правила `output` связано с типом `rust.target`.
[Синтетический пример](contracts/plugin-v1/examples/synthetic.json) использует
другие имена и ID на том же формате. Он не содержит коммерческих правил Arsenal.

Будущий Swift DSL должен создавать эквивалентный JSON и проходить эти же проверки.
Точные имена Swift типов не фиксируются сейчас: они не должны маскировать отсутствие
готового SDK или вводить второй исполнитель правил.

## 4. Факты и граница доступа

Rifle поддерживает в v1 типы `string` и `boolean`. Каждое переданное значение имеет
состояние `known(value)` или `unavailable(reason)`. Отсутствующий запрошенный факт —
ошибка адаптера `missing_fact`, а не `false`. Ошибка получения данных представляется
явно как `unavailable` и не превращается в успешную проверку отрицания.

| Источник BuildHunter | Тип | Точное значение |
|---|---|---|
| `node.name` | string | Последний компонент имени без пути, без нормализации и изменения регистра |
| `node.kind` | string | `directory`, `regular_file`, `symlink` или `other`; тип самой записи |
| `marker`, `scope: own` | boolean | Наличие обычного файла с заданным именем непосредственно внутри папки-кандидата |
| `marker`, `scope: parent` | boolean | Наличие обычного файла непосредственно в родительской папке кандидата |

Этот список источников закрыт для v1. `artifact ancestor` не является binding:
программа не получает состояние классификации предков. Решения о вложенности
и суммировании принимает BuildHunter после matching, как описано в разделе 6.

Для `own` у объекта, который не является папкой, значение равно `false` без чтения.
Имя маркера — один ASCII-компонент до 128 символов из букв, цифр, `_`, `-`, `.`;
`.` и `..` запрещены. Нет путей, glob, рекурсивного поиска или выхода через `/`.
Набор имён не зашит в Hunter: его предоставляет адаптер из всех активных bindings.

Предложение для v1: marker probe **не следует symlink**. Ссылка вместо обычного
файла даёт `false`. Ошибка доступа, облачный объект без локальных метаданных или
недоступная граница дают `unavailable(access_denied|cloud_skipped|out_of_scope|io_error)`.
Достоверное отсутствие или исчезновение до наблюдения даёт `false`; событие
исчезновения также передаётся существующей политике замечаний о меняющемся дереве.
Наблюдения не обещают атомарного snapshot файловой системы.

Проверка родителя корня скана не выходит за выбранное дерево: если родитель вне
него, факт `unavailable(out_of_scope)`. Обнаруженные symlink не становятся
артефактами v1; правила не могут заставить host следовать их целям. Ограничения
scope должны применяться в момент probe, включая гонку с заменой папки на ссылку.
Способ реализации на платформах требует отдельной проверки Hunter.

Сравнение строк — точное, без case folding и Unicode normalization, независимо
от настроек файловой системы. Если имя нельзя представить lossless Unicode,
`node.name` недоступен; запрещено сопоставлять правило с lossy display string.
Остальные факты могут оставаться известными. Точный путь/handle остаётся у host;
Rifle не получает путь для последующих действий. Успешное совпадение по другим
фактам не разрешает строить Finder URL из повреждённого отображаемого имени.

## 5. Язык условий и неизвестные значения

Разрешены только следующие формы; пустые `all`, `any`, `in` запрещены:

| Условие | Семантика |
|---|---|
| `fact + eq + value` | Равенство одного типа, без преобразований `true` ↔ `1` |
| `fact + in + values` | Равенство одному из значений того же типа |
| `fact + suffix + value` | Непустой суффикс строки; только для string |
| `all: [...]` | Логическое AND |
| `any: [...]` | Логическое OR |
| `not: condition` | Логическое отрицание |

Факт и все литералы должны иметь одинаковый объявленный тип. Regex, arbitrary
expressions, вызовы функций, переменные, рекурсия и внешние ссылки отсутствуют.

Результат каждого условия: `true`, `false` или `unknown`:

| Операция | Правило |
|---|---|
| `not unknown` | `unknown` |
| `all` | `false`, если есть false; иначе unknown, если есть unknown; иначе true |
| `any` | `true`, если есть true; иначе unknown, если есть unknown; иначе false |
| Проверка недоступного факта | `unknown` |

Таким образом, `not(marker == true)` не совпадает при отказе доступа. Для target
результаты связанных правил объединяются по той же OR-семантике. Короткое
замыкание допустимо; результат не должен зависеть от порядка вычисления.
Диагностика `unknown` содержит отсортированные ID недоступных фактов, необходимых
для ещё не определённого результата. Ошибки реально выполненных I/O host учитывает
отдельно: короткое замыкание не должно скрыть уже случившийся отказ доступа.

## 6. Совпадения, конфликты и исключения

Rifle возвращает rule ID и `true|false|unknown`, без выбора «лучшего» правила.
BuildHunter преобразует их в target results. Дубликаты ID пакетов или targets
во всём эффективном каталоге — ошибка загрузки, даже если определения одинаковы.
Порядок файлов, alphabetic order и источник пакета не определяют приоритет.

Для одного filesystem node после применения исключений пользователя:

- Один target `true`, остальные `false`: одна находка.
- Все `false`: нет находки; это не ошибка каталога.
- Два разных target `true`: `ambiguous_match` со всеми совпавшими ID. Не выбирать
  категорию и не добавлять две строки/двойной размер. Обход потомков продолжается.
- Нет `true`, но есть `unknown`: `indeterminate_match`, с причиной недоступных
  фактов; находка пока не подтверждена.
- Один `true` и хотя бы один `unknown`: `indeterminate_match`, поскольку нельзя
  доказать однозначность. Подтверждённый и неопределённые ID входят в диагностику.
- Два и более `true` плюс `unknown`: уже доказанная `ambiguous_match`; неизвестные
  кандидаты также сохраняются в диагностике.

Неоднозначность отмечает неполноту **классификации**, но не выдумывает ошибку
измерения байтов. Адаптер передаёт отдельный notice; отображение и итоговый статус
скана надо согласовать с действующими completed/partial/incomplete состояниями
до подключения runtime. Loader может выявить структурные конфликты заранее,
но не обещает доказать непересечение произвольных условий на всех деревьях.

У плагинов v1 нет поля `priority` или «override другого пакета». Автор устраняет
пересечение явными условиями либо пользователь отключает конфликтующий тип.
Базовые filter IDs сохраняются: доверенная конфигурация host резервирует нынешние
`swift.*`, `rust.*`, `python.*` за базовыми пакетами. Пакет не может сам объявить
себя доверенным через поле JSON; origin задаёт загрузчик. Дополнительные пакеты
используют свои namespace, включая пользовательские.

Исключения применяются до классификации: выключенные targets не вызывают probes
ради своих правил и не участвуют в конфликте. Настройки по-прежнему хранят target
IDs, включая временно неизвестные. Неизвестный ID не отключает похожий target.
Исключённый или уже найденный родитель не означает автоматического отсечения
потомков: политика вложенности принадлежит BuildHunter. Размер общей суммы
считается по внешним корням без повторного учёта вложенного объёма.

## 7. Загрузка, совместимость и воспроизводимость

Порядок загрузки до начала скана:

1. Проверить лимит размера и UTF-8; отклонить duplicate JSON keys, non-finite
   числа и некорректные Unicode sequences до потери информации парсером.
2. Проверить schema и точные версии форматов. Неизвестные поля и операторы —
   ошибка, а не игнорируемое расширение. Поддержка нового формата добавляется host.
3. Проверить уникальность ID, ссылки ruleIds, полное соответствие facts/bindings,
   типы и лимиты. Все объявленные факты используются хотя бы одним правилом;
   все правила принадлежат одному target. Тип binding должен совпадать с fact.
4. Проверить весь выбранный каталог, зарезервированные ID и конфликты загрузки.
5. Применить exclusions, подготовить immutable plan и зафиксировать его identity.

Повреждённый пакет не активируется частично. При невалидном необязательном
пользовательском пакете приложение предлагает явно исключить его и показывает
эффективный набор до старта; автоматического молчаливого fallback нет. Обязательный
пакет из поставки, включая Arsenal в платной сборке, должен пройти build-time и
runtime validation, иначе запуск соответствующего скана запрещён с диагностикой.
При конфликте ID нельзя автоматически выбрать один пакет; пользователь исправляет
выбор, после чего каталог валидируется заново.

JSON Schema описывает структуру по
[Draft 2020-12](https://json-schema.org/draft/2020-12/json-schema-core.html).
Для identity предложен SHA-256 от представления по
[JCS, RFC 8785](https://www.rfc-editor.org/rfc/rfc8785): package digest охватывает
весь JSON пакета. Fixtures и файлы авторского SDK в этот digest не входят.
Catalog digest — hash JCS массива `{id, version, digest}`, отсортированного по
ASCII ID пакета. Порядок полей JSON не влияет на digest; порядок массивов внутри
пакета сохраняется и может менять digest даже при одинаковом логическом результате.
В отчёт входят digest каталога, версии форматов, профиль клиента и отсортированные
exclusions. Digest подтверждает идентичность, а не доверие или авторство.

Смена version при том же ID не сбрасывает исключения. Один ID не переиспользуется
для другого смысла; удалённый тип не переназначается. Изменения в активном каталоге
влияют только на следующий scan. Диапазоны версий, автоматическая загрузка
зависимостей и online resolution не входят в v1; сборка закрепляет точные версии.

## 8. Ограничения стоимости и ошибки

Предлагаемые стартовые лимиты для review; до release их проверяют benchmark:

| Ресурс | Предел |
|---|---|
| JSON одного пакета | 1 MiB до разбора |
| Пакеты / суммарный JSON каталога | 64 / 16 MiB |
| Targets / rules / facts одного пакета | 256 / 256 / 128 |
| Targets / rules / уникальные marker probes каталога | 2048 / 4096 / 512 |
| Expression depth / nodes на правило | 8 / 128; корень имеет depth 1 |
| Children в all/any; литералы in | 32 |
| Все expression nodes эффективного каталога | 32768 |

Превышение — `limit_exceeded` до обхода. Это границы плана, не обещание общего
лимита RSS или постоянного времени проверки. Marker probes объединяются по
одинаковым scope/name. Безопасный candidate index может выдать лишнего кандидата,
но не пропустить возможное `true` или `unknown`. Для marker-only и отрицательных
правил нужен полный fallback среди разрешённых кандидатов, а не только index имён.

Адаптер отменяет дальнейший сбор фактов вместе со scan. Кэш маркеров живёт только
в scan, имеет отдельный измеряемый бюджет и не становится постоянным индексом.
Нельзя удерживать все увиденные пути ради acceleration. Конкретная стратегия
кэша и лимит pending work остаются задачей Hunter/BuildHunter, не полем плагина.

Диагностика имеет `code`, package ID, rule/target ID при наличии, JSON location
для ошибок загрузки, а для runtime — opaque node ID и fact ID. Примеры кодов:
`unsupported_format`, `invalid_shape`, `duplicate_id`, `unknown_fact`,
`type_mismatch`, `invalid_reference`, `limit_exceeded`, `reserved_id`,
`missing_fact`, `ambiguous_match`, `indeterminate_match`. Пользовательский текст
может локализоваться; код и идентификаторы стабильны внутри версии контракта.

## 9. Проверочные сценарии и миграция

Schema tests проверяют корректность примеров и отбрасывают неправильную структуру.
Они **не исполняют** правила. Следующая таблица — обязательные семантические тесты
для будущего Rust pilot; пока они не отмечены как пройденные:

| Сценарий | Ожидаемый результат |
|---|---|
| `target` + обычный `Cargo.toml` в доступном родителе | `rust.target` |
| `target` без `Cargo.toml`; обычный файл с именем target | Нет находки |
| Произвольное новое имя из синтетического пакета | Совпадение без правок scanner |
| Marker access denied и отрицание условия | unknown, не true |
| `any(true, unknown)` / `all(false, unknown)` | true / false |
| Родитель выбранного root вне scope | out_of_scope, чтения вне root нет |
| Symlink вместо маркера; замена родителя ссылкой между проверками | Не следовать ссылке |
| Невалидное Unicode имя | Нет lossy matching; точный host handle сохранён |
| Два true target; перестановка пакетов | Одинаковый ambiguous_match |
| Один true и один unknown | indeterminate_match |
| Выключен конфликтующий target | Его probes отсутствуют; конфликт исчезает |
| Найденный/исключённый родитель содержит другой артефакт | Потомки не теряются, общий объём не удваивается |
| Каталог/настройки меняются во время scan | Старый plan завершается неизменным |
| SDK export и вручную написанный эквивалентный JSON | Одинаковая программа и package digest при одинаковых данных |
| Marker-only rule / not / any при candidate indexing | Те же результаты, что у полного перебора |
| Stop во время probes; файл исчезает; облачный объект выгружен | Текущие lifecycle/cloud гарантии и соответствующие fact outcomes |

C2 (CLI/GUI defaults и классификация environments), C3 (symlink markers), C4
(lossless пути) требуют явной миграции. В частности no-follow и unknown name —
предложенные v1 правила, не описание нынешнего поведения. Старые результаты
сравниваются с новым pilot, а ожидаемые различия перечисляются отдельно.
Не следует объявлять parity, изменив одновременно baseline и правила.

Перед реализацией нужно принять предлагаемые: unknown/ambiguity policy,
no-follow/scope policy и лимиты. После этого первый implementation PR — чистый
Rifle evaluator и semantic tests из таблицы. Затем адаптер получения фактов,
проверка на filesystem fixtures и Release comparison; только после этого
подключение к текущему scanner. ABI, Swift API, UI импорта и отображение
classification notices проектируются отдельными небольшими изменениями.
